# SWD Commerce Platform — Delivery Notes

Everything in the original build spec that is achievable without an
external account (a live database host, a live Flutterwave merchant
account, a live email-provider key) has been built and verified. The
three things that remain are genuinely irreducible — see section K.

## A. What was built

**Storefront**
- Product catalogue (`/products`) — search, category filters
- Product detail pages (`/products/[slug]`) — variants, images,
  price, shipping cost, delivery estimate, stock status, add-to-cart,
  buy-now, related products
- Cart (`/cart`) — client-side, persisted to localStorage
- Checkout (`/checkout`) — name/email/phone/country/city/address/
  delivery instructions, plus a coupon-code field with live validation

**Orders & payment**
- Order numbers: `SWD-<year>-<6-digit sequence>`, generated by an
  atomic Postgres upsert-increment (`order_counters` table) — safe
  under concurrent checkouts, verified by an integration test that
  fires 25 concurrent requests and checks for zero collisions
- All 14 order statuses from the spec
- Payment abstraction (`lib/payments/types.ts`), implemented for
  Flutterwave; adding a second gateway means implementing the
  interface and registering it, not touching checkout/webhook code
- Payment verification never trusts the frontend or the webhook
  payload alone: the webhook checks `verif-hash` against
  `FLUTTERWAVE_SECRET_HASH`, then re-verifies the transaction directly
  against Flutterwave's API. The order-return page does the same for
  immediate feedback. Both share one idempotent function
- Public order tracking (`/order/[orderNumber]`)

**Suppliers & fulfillment**
- Supplier records — `/admin/suppliers`
- Per-product supplier mapping (SKU, cost, shipping, stock, URL,
  processing time, delivery estimate) — set in `/admin/products`
- Manual fulfillment: "Send to Supplier" and "mark shipped" forms on
  each order, both updating status and the tracking-event log

**Coupons**
- `/admin/coupons` — create (code, percent-off or amount-off,
  optional expiry), activate/deactivate
- `/api/coupons/validate` — checks active + not-expired before the
  checkout form shows a discount
- Checkout re-validates server-side regardless of what the client
  claims, computes the discount from the coupon row, and stores
  `discountTotal` on the order — verified end-to-end (a 10%-off coupon
  on a $50 item correctly produced `discountTotal: 5, total: 49` in
  the database, not just in the UI)

**Profit engine**
- `lib/profit.ts` — gross margin, contribution margin, and rates from
  selling price, shipping, supplier cost, payment fees, advertising
  cost, refund reserve
- Surfaced on the admin dashboard (aggregate) and each order detail
  page (per-order)

**Admin dashboard** (`/admin`)
- Dashboard, Orders (list + detail with status/fulfillment/tracking
  actions), Products, Suppliers, Coupons, Payments, Fulfillment,
  Settings — all backed by real data
- Shipping / Marketing / Analytics: honest placeholders explaining
  what's needed to build them, not fake screens

**Admin authentication (multi-user)**
- Real `admins` table — bcrypt-hashed passwords, one row per admin
- Signed, expiring session tokens (HMAC via Web Crypto, so the
  Edge-runtime `proxy.ts` middleware can verify them without a Node
  dependency)
- `/admin/settings` lists admins and lets a logged-in admin create
  more; the very first admin is created via a one-time bootstrap
  script (`lib/db/seed-admin.ts`) since nobody can log in to create
  themselves
- Timing-safe comparisons throughout; a lookup for a non-existent
  email still runs a dummy bcrypt comparison so response time doesn't
  leak which emails have accounts

**Rate limiting**
- Postgres-backed (row-locked transactions — Vercel serverless
  functions share no memory across invocations, so an in-process
  counter would not actually limit anything)
- Applied to `/api/checkout` (20 per 10 minutes per IP) and
  `/api/admin/login` (10 per 15 minutes per IP)
- Verified: 20 concurrent requests against a limit of 5 correctly let
  exactly 5 through, never more, under real concurrency

**Notifications**
- `NotificationChannel` abstraction (`lib/notifications/types.ts`),
  implemented for email via Resend
- Wired into order-received, payment-confirmed, shipped, and
  delivered — every order-lifecycle event the spec asked for
- Safely no-ops (with a log line) when no provider is configured, so
  checkout and admin actions never fail because notifications aren't
  set up yet

**Automated tests** (`npm test`, 26 tests, all passing)
- Unit tests: checkout pricing math, profit-engine math, coupon
  discount math, Flutterwave webhook signature verification
  (including the "prefix of the real hash" attack case)
- Integration tests against a real Postgres instance: order-number
  atomicity under 25 concurrent calls, rate-limiter correctness under
  20 concurrent calls against a limit of 5

**Demo data**
- One supplier, one category, and the specified demo product —
  "Portable Blender (DEMO)", $50 selling / $20 supplier cost / $6
  supplier shipping / $4 customer shipping — all clearly labeled
  DEMO/TEST DATA in the UI

## B. Database / schema

**Drizzle ORM** (switched from Prisma — its binary query engines
couldn't be fetched in this build environment's network allowlist;
Drizzle is also a better fit for Vercel serverless generally, no
binary engine to bundle or cold-start).

**PostgreSQL** (switched from an initial SQLite prototype — Vercel's
serverless filesystem is ephemeral and read-only, so SQLite cannot
work there). Built and tested against a local Postgres instance in
this environment.

Tables: `customers`, `admins`, `categories`, `suppliers`, `products`,
`product_variants`, `orders`, `order_items`, `payments`,
`fulfillments`, `tracking_events`, `order_counters`, `coupons`,
`rate_limits`, `audit_logs`.

Migrations: `npx drizzle-kit push` (schema-in-code, pushed directly).
Switch to `drizzle-kit generate` + versioned migration files once this
has real production data you don't want to risk with `push`.

## C. API endpoints

- `POST /api/checkout` — re-prices from the DB, validates any coupon
  server-side, creates customer/order/order-items/payment, initiates
  payment, sends the order-received notification, returns a redirect URL
- `POST /api/webhooks/flutterwave` — verified async payment callback
- `POST /api/orders/[orderNumber]/verify` — same verification logic,
  called on return from Flutterwave for immediate feedback
- `POST /api/coupons/validate` — checks a code before checkout submits
- `POST /api/admin/login` / `POST /api/admin/logout` — admin session
- `POST /api/admin/dsers/sync-order` — admin-only; pushes a paid
  order's items/shipping details to DSers (see section M)
- `POST /api/webhooks/dsers` — verified fulfillment-status callback
  from DSers (tracking number, carrier, shipped/delivered)
- Admin mutations (order status, send-to-supplier, tracking, product/
  supplier/category/coupon/admin creation) are Server Actions
  (`lib/admin-actions.ts`)

## E. Payment integration steps (Flutterwave)

1. Create a Flutterwave account (test/sandbox mode first)
2. Dashboard → Settings → API: get your Public Key and Secret Key
3. Dashboard → Settings → Webhooks: set a secret hash (any random
   string) and also set it as `FLUTTERWAVE_SECRET_HASH`
4. Set the webhook URL to `https://<your-domain>/api/webhooks/flutterwave`
5. Add all three `FLUTTERWAVE_*` variables to Vercel
6. Test with Flutterwave's sandbox cards before switching to live keys

**Merchant-of-record confirmation**: payment is collected into SWD's
own Flutterwave account only — no split-payment or marketplace-payout
call exists anywhere in the code. Supplier cost in `fulfillments` is
pure bookkeeping (what SWD owes the supplier), paid however SWD
chooses, triggered manually via "Send to Supplier."

## F. Supplier integration steps (current: manual, Phase 2)

1. Add a supplier in `/admin/suppliers`
2. When adding a product in `/admin/products`, select that supplier
   and fill in supplier SKU/cost/shipping/stock
3. On a paid order, use "Send to Supplier" once you've actually placed
   the order with them
4. Once shipped, use "Tracking & carrier" to record the tracking
   number — this also sends the shipped-notification email if
   configured

## M. Supplier API integration (DSers) — Phase 3

Built as an addition on top of the manual flow above, not a
replacement — "Send to Supplier" still works for non-DSers suppliers.

- `POST /api/admin/dsers/sync-order` (`{ orderId }`) — requires an
  admin session; refuses to run on an unpaid order, refuses if any
  line item's product has no `dsers_product_id` mapped, and is
  idempotent (re-calling it on an already-synced order returns the
  existing `dsersOrderId` instead of sending a duplicate). On success
  it creates/updates the order's `fulfillments` row
  (`status: "sent"`, `dsersOrderId` set) and moves the order to
  `SUPPLIER_ORDERED`.
- `POST /api/webhooks/dsers` — verifies the shared-secret header,
  looks up the order by the `dsersOrderId` stored during sync,
  upserts `trackingNumber`/`carrier`/`trackingUrl` into
  `fulfillments`, and sets `orders.fulfillmentStatus = "fulfilled"`
  (plus the fuller `orders.status`: `SHIPPED`/`DELIVERED`/`CANCELLED`
  depending on the payload). Idempotent — a duplicate webhook delivery
  that changes nothing is a no-op.
- `lib/dsers.ts` holds the request/response shaping, the webhook
  signature check, and the DSers-status → internal-status mapping in
  one place — same pattern as `lib/payments/flutterwave.ts`. The
  exact endpoint path, field names, and webhook header are a
  reasonable default; confirm them against your actual DSers
  account/docs before relying on this live (noted in the file).
- **Merchant-of-record boundary preserved**: this integration only
  ever exchanges fulfillment data (order + shipping details out,
  tracking status in). Nothing here authorizes a payment or lets
  DSers charge the customer or get paid directly — SWD pays/manages
  DSers as its own separate, SWD-controlled operation, same as the
  manual "Send to Supplier" flow.

Phase 4 (marketing automation) is still not built — no spec yet for
what it should send or to whom.

## H. Order flow: customer → payment → supplier → tracking

1. Customer checks out; `/api/checkout` re-prices everything from the
   database, validates any coupon server-side, creates the order as
   `PAYMENT_PENDING`, snapshots supplier cost on each line item, and
   asks Flutterwave for a hosted checkout link. An order-received
   email is sent (if configured)
2. Customer pays on Flutterwave's page
3. Flutterwave redirects to `/order/[orderNumber]`, which triggers an
   immediate re-verification call
4. Flutterwave also calls the webhook asynchronously — the
   authoritative path. Both call the same idempotent
   `applyVerifiedPayment()`
5. Once verified: order → `PAID`, a `payment_confirmed` tracking
   event is recorded, and a payment-confirmed email is sent
6. Admin places the order with the supplier, clicks "Send to
   Supplier" (→ `SUPPLIER_ORDERED`)
7. Admin enters tracking once shipped (→ `SHIPPED`, shipped-email sent)
8. Customer checks `/order/[orderNumber]` any time for the status
   timeline

## I. Security considerations

- Payment amounts/status are always re-verified against Flutterwave's
  API — never trusted from the client or the webhook payload alone
- Webhook signature checked with a constant-time comparison
- Checkout re-prices every line item (and re-validates any coupon)
  from the database — a manipulated client-side cart cannot change
  what's charged
- Admin routes gated by `proxy.ts` checking a signed, expiring session
  token; no admin page renders without one
- Multi-admin auth: bcrypt-hashed passwords, timing-safe comparisons,
  a dummy hash comparison on unknown emails to avoid leaking which
  accounts exist via response timing
- Rate limiting on checkout and admin login, enforced atomically via
  Postgres row locks (correct under real concurrency, not just
  "probably fine in practice")
- Secrets read from environment variables only, never hard-coded or
  sent to the client
- Idempotency: `applyVerifiedPayment()` checks
  `payment.status === "successful"` first, so duplicate webhook
  deliveries (which gateways routinely send) don't double-process

## J. Automated tests

```
npm test        # unit + integration (Vitest)
npm run test:e2e  # browser tests (Playwright) — needs the app buildable/startable
```

33 Vitest tests across 7 files — unit tests (pricing, profit engine,
coupon math, Flutterwave/DSers webhook signature verification,
notification channel dispatch) plus 2 integration-test files that run
against a real Postgres database (order-number atomicity, rate-limit
correctness), both exercising real concurrency rather than asserting
against a single call. `vitest.config.ts` / `vitest.setup.ts` load
`.env` automatically; the integration tests need `DATABASE_URL` set
there, pointed at a non-production database — they insert real rows.

Browser coverage added via Playwright (`e2e/`): admin-auth boundary
(redirect-to-login, preserved `?next=`, bad-credentials error) and
storefront navigation (homepage, product search, cart). These run
`next build && next start` against whatever `DATABASE_URL` is
configured, so point `.env.local` at a non-production database before
running them if you'd rather not exercise read queries against live
data. `playwright.config.ts` supports `PLAYWRIGHT_CHROMIUM_PATH` to
point at a pre-installed Chromium binary instead of downloading one
(useful in sandboxed CI).

Not covered yet: the checkout → payment → webhook round trip
end-to-end (would need a Flutterwave sandbox account to test against
honestly, rather than mocking the one API call that matters most), and
a real DSers sandbox round trip (same reason — `DSERS_API_URL`/
`DSERS_API_KEY` from a real DSers account).

## K. What genuinely cannot be finished without your own accounts

No amount of further code changes closes these — they need
credentials only you can obtain:

1. **A production Postgres host.** This was built and tested against
   local Postgres in the build environment. Provision one (Neon,
   Supabase, Vercel Postgres, RDS, etc.), then run
   `DATABASE_URL=<production-url> npx drizzle-kit push` once, and
   create your first admin against that same URL.
2. **Real Flutterwave credentials.** The integration is built and
   code-reviewed against Flutterwave's documented API shape, and its
   failure path (missing credentials) is verified working — but no
   actual successful payment has run in this environment, because
   that requires your Flutterwave account.
3. **A Resend (or other) API key**, if you want order emails to
   actually send rather than log a skip line.
