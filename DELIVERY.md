# SWD Commerce Platform — Delivery Notes

Everything in the original build spec that is achievable without an
external account (a live database host, a live Flutterwave merchant
account, a live email-provider key) has been built and verified. The
three things that remain are genuinely irreducible — see section K.

## A. What was built

**Storefront**
- Product catalogue (`/products`) — search, category filters
- Product detail pages (`/products/[slug]`) — variants, images,
  price, shipping cost, delivery estimate, stock status, add-to-cart,
  buy-now, related products
- Cart (`/cart`) — client-side, persisted to localStorage
- Checkout (`/checkout`) — name/email/phone/country/city/address/
  delivery instructions, plus a coupon-code field with live validation

**Orders & payment**
- Order numbers: `SWD-<year>-<6-digit sequence>`, generated by an
  atomic Postgres upsert-increment (`order_counters` table) — safe
  under concurrent checkouts, verified by an integration test that
  fires 25 concurrent requests and checks for zero collisions
- All 14 order statuses from the spec
- Payment abstraction (`lib/payments/types.ts`), implemented for
  Flutterwave; adding a second gateway means implementing the
  interface and registering it, not touching checkout/webhook code
- Payment verification never trusts the frontend or the webhook
  payload alone: the webhook checks `verif-hash` against
  `FLUTTERWAVE_SECRET_HASH`, then re-verifies the transaction directly
  against Flutterwave's API. The order-return page does the same for
  immediate feedback. Both share one idempotent function
- Public order tracking (`/order/[orderNumber]`)

**Suppliers & fulfillment**
- Supplier records — `/admin/suppliers`
- Per-product supplier mapping (SKU, cost, shipping, stock, URL,
  processing time, delivery estimate) — set in `/admin/products`
- Manual fulfillment: "Send to Supplier" and "mark shipped" forms on
  each order, both updating status and the tracking-event log

**Coupons**
- `/admin/coupons` — create (code, percent-off or amount-off,
  optional expiry), activate/deactivate
- `/api/coupons/validate` — checks active + not-expired before the
  checkout form shows a discount
- Checkout re-validates server-side regardless of what the client
  claims, computes the discount from the coupon row, and stores
  `discountTotal` on the order — verified end-to-end (a 10%-off coupon
  on a $50 item correctly produced `discountTotal: 5, total: 49` in
  the database, not just in the UI)

**Profit engine**
- `lib/profit.ts` — gross margin, contribution margin, and rates from
  selling price, shipping, supplier cost, payment fees, advertising
  cost, refund reserve
- Surfaced on the admin dashboard (aggregate) and each order detail
  page (per-order)

**Admin dashboard** (`/admin`)
- Dashboard, Orders (list + detail with status/fulfillment/tracking
  actions), Products, Suppliers, Coupons, Payments, Fulfillment,
  Settings — all backed by real data
- Shipping / Marketing / Analytics: honest placeholders explaining
  what's needed to build them, not fake screens

**Admin authentication (multi-user)**
- Real `admins` table — bcrypt-hashed passwords, one row per admin
- Signed, expiring session tokens (HMAC via Web Crypto, so the
  Edge-runtime `proxy.ts` middleware can verify them without a Node
  dependency)
- `/admin/settings` lists admins and lets a logged-in admin create
  more; the very first admin is created via a one-time bootstrap
  script (`lib/db/seed-admin.ts`) since nobody can log in to create
  themselves
- Timing-safe comparisons throughout; a lookup for a non-existent
  email still runs a dummy bcrypt comparison so response time doesn't
  leak which emails have accounts

**Rate limiting**
- Postgres-backed (row-locked transactions — Vercel serverless
  functions share no memory across invocations, so an in-process
  counter would not actually limit anything)
- Applied to `/api/checkout` (20 per 10 minutes per IP) and
  `/api/admin/login` (10 per 15 minutes per IP)
- Verified: 20 concurrent requests against a limit of 5 correctly let
  exactly 5 through, never more, under real concurrency

**Notifications**
- `NotificationChannel` abstraction (`lib/notifications/types.ts`),
  implemented for email via Resend
- Wired into order-received, payment-confirmed, shipped, and
  delivered — every order-lifecycle event the spec asked for
- Safely no-ops (with a log line) when no provider is configured, so
  checkout and admin actions never fail because notifications aren't
  set up yet

**Automated tests** (`npm test`, 26 tests, all passing)
- Unit tests: checkout pricing math, profit-engine math, coupon
  discount math, Flutterwave webhook signature verification
  (including the "prefix of the real hash" attack case)
- Integration tests against a real Postgres instance: order-number
  atomicity under 25 concurrent calls, rate-limiter correctness under
  20 concurrent calls against a limit of 5

**Demo data**
- One supplier, one category, and the specified demo product —
  "Portable Blender (DEMO)", $50 selling / $20 supplier cost / $6
  supplier shipping / $4 customer shipping — all clearly labeled
  DEMO/TEST DATA in the UI

## B. Database / schema

**Drizzle ORM** (switched from Prisma — its binary query engines
couldn't be fetched in this build environment's network allowlist;
Drizzle is also a better fit for Vercel serverless generally, no
binary engine to bundle or cold-start).

**PostgreSQL** (switched from an initial SQLite prototype — Vercel's
serverless filesystem is ephemeral and read-only, so SQLite cannot
work there). Built and tested against a local Postgres instance in
this environment.

Tables: `customers`, `admins`, `categories`, `suppliers`, `products`,
`product_variants`, `orders`, `order_items`, `payments`,
`fulfillments`, `tracking_events`, `order_counters`, `coupons`,
`rate_limits`, `audit_logs`.

Migrations: `npx drizzle-kit push` (schema-in-code, pushed directly).
Switch to `drizzle-kit generate` + versioned migration files once this
has real production data you don't want to risk with `push`.

## C. API endpoints

- `POST /api/checkout` — re-prices from the DB, validates any coupon
  server-side, creates customer/order/order-items/payment, initiates
  payment, sends the order-received notification, returns a redirect URL
- `POST /api/webhooks/flutterwave` — verified async payment callback
- `POST /api/orders/[orderNumber]/verify` — same verification logic,
  called on return from Flutterwave for immediate feedback
- `POST /api/coupons/validate` — checks a code before checkout submits
- `POST /api/admin/login` / `POST /api/admin/logout` — admin session
- `POST /api/admin/dsers/sync-order` — admin-only; pushes a paid
  order's items/shipping details to DSers (see section M)
- `POST /api/webhooks/dsers` — verified fulfillment-status callback
  from DSers (tracking number, carrier, shipped/delivered)
- Admin mutations (order status, send-to-supplier, tracking, product/
  supplier/category/coupon/admin creation) are Server Actions
  (`lib/admin-actions.ts`)
- `GET /oraimo` — Oraimo brand landing page (see section N)
- `GET /products?brand=<name>` — brand-filtered catalogue, combinable
  with `?category=` and `?q=`

## E. Payment integration steps (Flutterwave)

1. Create a Flutterwave account (test/sandbox mode first)
2. Dashboard → Settings → API: get your Public Key and Secret Key
3. Dashboard → Settings → Webhooks: set a secret hash (any random
   string) and also set it as `FLUTTERWAVE_SECRET_HASH`
4. Set the webhook URL to `https://<your-domain>/api/webhooks/flutterwave`
5. Add all three `FLUTTERWAVE_*` variables to Vercel
6. Test with Flutterwave's sandbox cards before switching to live keys

**Merchant-of-record confirmation**: payment is collected into SWD's
own Flutterwave account only — no split-payment or marketplace-payout
call exists anywhere in the code. Supplier cost in `fulfillments` is
pure bookkeeping (what SWD owes the supplier), paid however SWD
chooses, triggered manually via "Send to Supplier."

## F. Supplier integration steps (current: manual, Phase 2)

1. Add a supplier in `/admin/suppliers`
2. When adding a product in `/admin/products`, select that supplier
   and fill in supplier SKU/cost/shipping/stock
3. On a paid order, use "Send to Supplier" once you've actually placed
   the order with them
4. Once shipped, use "Tracking & carrier" to record the tracking
   number — this also sends the shipped-notification email if
   configured

## M. Supplier API integration (DSers) — Phase 3

Built as an addition on top of the manual flow above, not a
replacement — "Send to Supplier" still works for non-DSers suppliers.

- `POST /api/admin/dsers/sync-order` (`{ orderId }`) — requires an
  admin session; refuses to run on an unpaid order, refuses if any
  line item's product has no `dsers_product_id` mapped, and is
  idempotent (re-calling it on an already-synced order returns the
  existing `dsersOrderId` instead of sending a duplicate). On success
  it creates/updates the order's `fulfillments` row
  (`status: "sent"`, `dsersOrderId` set) and moves the order to
  `SUPPLIER_ORDERED`.
- `POST /api/webhooks/dsers` — verifies the shared-secret header,
  looks up the order by the `dsersOrderId` stored during sync,
  upserts `trackingNumber`/`carrier`/`trackingUrl` into
  `fulfillments`, and sets `orders.fulfillmentStatus = "fulfilled"`
  (plus the fuller `orders.status`: `SHIPPED`/`DELIVERED`/`CANCELLED`
  depending on the payload). Idempotent — a duplicate webhook delivery
  that changes nothing is a no-op.
- `lib/dsers.ts` holds the request/response shaping, the webhook
  signature check, and the DSers-status → internal-status mapping in
  one place — same pattern as `lib/payments/flutterwave.ts`. The
  exact endpoint path, field names, and webhook header are a
  reasonable default; confirm them against your actual DSers
  account/docs before relying on this live (noted in the file).
- **Merchant-of-record boundary preserved**: this integration only
  ever exchanges fulfillment data (order + shipping details out,
  tracking status in). Nothing here authorizes a payment or lets
  DSers charge the customer or get paid directly — SWD pays/manages
  DSers as its own separate, SWD-controlled operation, same as the
  manual "Send to Supplier" flow.

Phase 4 (marketing automation) is still not built — no spec yet for
what it should send or to whom.

## G. How to create a product

Admin → Products → "Add product." Requires SKU, title, category,
selling price, description, and a **Fulfilment** choice:

- **SWD inventory** (default) — also requires a supplier. Sold and
  shipped through SWD's own checkout, same as every product before

- **Affiliate link** — requires an affiliate URL instead of a

make the product appear in that brand's filtered view at
`/products?brand=<name>` and, for Oraimo specifically, on `/oraimo`.

## H. Order flow: customer → payment → supplier → tracking

1. Customer checks out; `/api/checkout` re-prices everything from the
   database, validates any coupon server-side, creates the order as
   `PAYMENT_PENDING`, snapshots supplier cost on each line item, and
   asks Flutterwave for a hosted checkout link. An order-received
   email is sent (if configured)
2. Customer pays on Flutterwave's page
3. Flutterwave redirects to `/order/[orderNumber]`, which triggers an
   immediate re-verification call
4. Flutterwave also calls the webhook asynchronously — the
   authoritative path. Both call the same idempotent
   `applyVerifiedPayment()`
5. Once verified: order → `PAID`, a `payment_confirmed` tracking
   event is recorded, and a payment-confirmed email is sent
6. Admin places the order with the supplier, clicks "Send to
   Supplier" (→ `SUPPLIER_ORDERED`)
7. Admin enters tracking once shipped (→ `SHIPPED`, shipped-email sent)
8. Customer checks `/order/[orderNumber]` any time for the status
   timeline

## I. Security considerations

- Payment amounts/status are always re-verified against Flutterwave's
  API — never trusted from the client or the webhook payload alone
- Webhook signature checked with a constant-time comparison
- Checkout re-prices every line item (and re-validates any coupon)
  from the database — a manipulated client-side cart cannot change
  what's charged
- Admin routes gated by `proxy.ts` checking a signed, expiring session
  token; no admin page renders without one
- Multi-admin auth: bcrypt-hashed passwords, timing-safe comparisons,
  a dummy hash comparison on unknown emails to avoid leaking which
  accounts exist via response timing
- Rate limiting on checkout and admin login, enforced atomically via
  Postgres row locks (correct under real concurrency, not just
  "probably fine in practice")
- Secrets read from environment variables only, never hard-coded or
  sent to the client
- Idempotency: `applyVerifiedPayment()` checks
  `payment.status === "successful"` first, so duplicate webhook
  deliveries (which gateways routinely send) don't double-process

## O. SWD Business OS — Phase 1 (Foundation)

The SWD Business OS Document Pack (charter, architecture, RBAC spec,
roadmap) describes a much larger internal operations platform —
Sales & POS, Inventory, Customers, Suppliers, Repair Management, Cash
Management, Staff Management, Reports, SOPs, offline POS. Per its own
roadmap, **Phase 1 (Foundation) — employee accounts, roles,
permissions, audit logging, navigation, dashboard — is what's built
and live now**; every other module is a real, honestly-labeled "Coming
soon" tile on the dashboard, not a working screen, per the pack's own
rule: "do not build decorative buttons that do nothing."

**What exists:**
- `admins` table extended (migration `0004_business_os_foundation.sql`,
  purely additive): `employee_number`, `staff_role` (defaults every
  existing admin to `OWNER` — unchanged effective access), `active`.
- `audit_logs` table — append-only, inserted from `lib/audit.ts`'s
  `recordAuditEvent()`. A logging failure is caught and logged, never
  allowed to fail the action it's recording.
- `lib/rbac.ts` — the four Business OS roles (OWNER/MANAGER/CASHIER/
  TECHNICIAN) and a fixed permission table per
  `05_Roles_Permissions_and_Access_Control.md`, checked via
  `hasPermission(role, permission)`. Default-deny: an unknown/null role
  is granted nothing. Unit-tested in `lib/__tests__/rbac.test.ts`.
- Session tokens now carry `staffRole` (`lib/admin-auth.ts`); a
  deactivated employee (`active = false`) is refused a new session at
  login even with the correct password — checked server-side in
  `checkAdminCredentials`, not just hidden in the UI. (An already-issued
  session keeps working until its 8-hour expiry, same as any other
  revocation in this token design — documented, not silently assumed.)
- `/admin/business-os` — the eight-module dashboard from the reference
  design. Each tile is permission-gated: unopened modules show "Coming
  soon" (not built yet) or "No access" (built, but this role can't open
  it) rather than a dead link.
- `/admin/business-os/staff` — **Staff Management, fully working**:
  list employees, create an account (name/email/temp password/employee
  number/role), change a role, deactivate/reactivate. Every mutation is
  gated server-side by `staff.manage` (`lib/admin-actions.ts`:
  `createStaffAccount`, `setStaffRole`, `setStaffActive` — the page
  itself also checks permission before rendering the form, but the
  server action is the real gate), and every create/role-change/
  activation-change is written to `audit_logs`. Two guard rails beyond
  the spec's base requirements: an admin can't deactivate their own
  account, and the last remaining `OWNER` can't be demoted (both would
  otherwise be able to lock every admin out of the system).
- Nav link added to the existing admin sidebar (`app/admin/layout.tsx`).

**Verified in this build environment** against a real local Postgres
(schema push, `npx next build` production build including the two new

## P. SWD Business OS — Phase 2 (Inventory ledger)

- `/admin/business-os/inventory`: on-hand quantities, low-stock flags
  (`products.reorder_level`), stock value at cost, recent movements, and a
  "record stock movement" form (purchase receipt, customer/supplier return,
  adjustment in/out, damage, loss). `inventory.manage` required server-side;
  adjustments/damage/loss require a written reason; every movement is audited.
- Ledger: `inventory_movements` is append-only (a Postgres trigger rejects
  UPDATE/DELETE), `inventory_balances` holds the per-location running
  quantity, and `products.stock` mirrors the total so the online storefront is
  unchanged. All three change in one transaction with the balance row locked
  (`lib/inventory.ts` `applyStockMovement`) — tested with 15 concurrent
  removals against 10 units: exactly 10 succeed, stock ends at 0.
- Migration `0004_business_os_inventory.sql` (replaces the unjournaled
  hand-written foundation file; it contains both). It backfills existing
  `products.stock` as `OPENING_BALANCE` ledger entries. Verified on a scratch
  Postgres (backfill + trigger). **Known pre-existing issue:** migrations
  0000–0003 can't replay on an empty database (0001 has an invalid
  `ALTER ... TYPE serial`); production was built with `drizzle-kit push`, so
  apply this to production with `npx drizzle-kit push` (additive only) after a
  Neon backup/branch, or run the 0004 SQL by hand.
- Not yet: stocktake, product variants in the ledger, multi-location UI,
  stock valuation by FIFO/average cost, and POS/purchase flows that will
  post SALE / PURCHASE_RECEIPT movements automatically. Online checkout does
  not yet post SALE ledger entries — flagged for the POS/orders integration.

## Q. SWD Business OS — Phase 3 (Sales & POS, cash)

- `/admin/business-os/pos`: till (search by name/SKU, cart, discount, cash
  tendered/change), recent sales; printable receipt at
  `/admin/business-os/pos/receipt/<SWD-R-YYYY-NNNNNN>`; return/refund form on
  the receipt for manager/owner only (`pos.refund`).
- `createSale` (`lib/sales.ts`) is one transaction: re-prices from the DB
  (the browser sends only product ids + quantities), writes sale, items
  (title/price/cost snapshot) and cash payment, posts `SALE` ledger
  movements (rolling the whole sale back if stock would go negative), mints
  a gap-free receipt number. A per-cart idempotency key makes a retry or
  double-click return the original receipt. Returns post `CUSTOMER_RETURN`
  movements and refund pro-rated for the sale discount, capped at units sold.
- **Safe defaults chosen by me, pending your decision** (pack §12.3):
  cash only; discount limits Cashier 0% / Manager 10% / Owner any
  (`DISCOUNT_LIMIT_PERCENT` in `lib/pos.ts`); refunds manager/owner only with
  no amount threshold. Mobile money/card are deliberately not enabled: they
  need a separate verification step, never a staff-typed reference.
- Bug found and fixed while testing in a real browser: production's DB pool
  is a single connection (`max: 1`), and `applyStockMovement` looked up the
  default location through the global connection while inside a transaction,
  which hung forever. The Vitest pool is 10, so ordinary tests could not see
  it. Fixed, and `single-connection.integration.test.ts` reruns a sale +
  return on a 1-connection pool (`DB_POOL_MAX`); it times out without the fix.
  **Rule going forward: inside a transaction, use `tx`, never `db`.**
- Not yet: cash sessions/till reconciliation (next phase), voiding a sale,
  customer records linked to sales (name/phone are free text for now),
  mobile money/card, offline mode, tax. Online store orders still don't post
  to the ledger.
- Tests: 86 passing (incl. concurrent sales never oversell, idempotent
  double-submit, rollback, discount limits, refund pro-rating).

## R. SWD Business OS — Phase 4 (Cash management)

- `/admin/business-os/cash`: open a session with a float; record expenses,
  withdrawals, deposits (reason required); close with a counted amount;
  session history. Cashiers see only their own sessions and are **not shown
  the expected total until they close** (blind count); managers/owners see
  everything.
- Rules (`lib/cash.ts`, unit-tested): expected = float + cash sales − cash
  refunds − expenses − withdrawals + deposits (+ signed corrections);
  variance = counted − expected; any variance needs a written explanation;
  |variance| > 5,000 UGX leaves the session `PENDING_APPROVAL` until a
  *different* user with `cash.reconcile` approves it. Closed sessions are
  never edited — a manager/owner posts a signed `CORRECTION` movement with a
  reason. All of it is audited.
- **Sales and refunds now require an open session** (`sales.cash_session_id`,
  `sale_returns.cash_session_id`): no session, no cash sale; a refund comes
  out of the processing employee's drawer. One open session per employee is
  enforced by a partial unique index. `cash_movements` is append-only (DB
  trigger).
- Migration `0005_business_os_cash.sql` also creates the POS tables from
  Phase 3 (they had been applied with `push` only). Same deploy note as
  Phase 2: apply with `drizzle-kit push` after a Neon backup/branch, then run
  the two trigger statements at the end of 0005 (push does not create
  triggers; same for the Phase 2 ledger trigger in 0004).
- **Defaults I chose, pending your decision:** 5,000 UGX variance threshold
  (`CASH_VARIANCE_THRESHOLD`); self-approval blocked; cash only, so there is
  no mobile-money/bank/card reconciliation yet.
- Known UX gap (same as the rest of the admin): a rejected action such as
  closing with a variance but no note shows Next's generic "This page
  couldn't load" error instead of an inline message. The POS till already
  shows inline errors; the admin forms should be moved to the same pattern.
- Verified in a browser: sale blocked with no session; open → sell → close
  short by 10,000 → pending → cashier can't approve → manager approves →
  CLOSED, with audit entries. 100 tests pass.

## S. SWD Business OS — Phase 5 (Purchasing, goods receiving, supplier balances)

- `/admin/business-os/purchasing` (the dashboard's Suppliers card now opens
  here; the dropshipping directory is still at `/admin/suppliers`) and
  `/admin/business-os/purchasing/<SWD-PO-YYYY-NNNNNN>`.
- Flow: create PO (multi-line, supplier, unit costs) → pending approval →
  approve → receive (partial deliveries, rejected units with a reason) →
  record supplier invoice → record payment. **A PO never changes stock; only a
  goods receipt does**, posting `PURCHASE_RECEIPT` ledger movements at the PO
  unit cost. Receiving locks the PO row, so two simultaneous receipts can't
  exceed the ordered quantity (tested); payments lock the supplier row so two
  can't overpay the balance (tested). Cancel is allowed only before anything is
  received.
- Permissions: create/cancel/invoice = `suppliers.manage`; approve and pay =
  `purchasing.approve` (manager/owner); receive = `inventory.manage`. All
  audited.
- **Defaults I chose, pending your decision:** a manager can't approve their own
  PO (an owner can); POs above 1,000,000 UGX need the owner
  (`PO_OWNER_APPROVAL_THRESHOLD` in `lib/purchasing.ts`). Supplier payment is
  *recorded* here (money paid by SWD outside the app); it never goes through
  the customer gateway and the app moves no money.
- Migration `0006_business_os_purchasing.sql` (additive). Apply the same way
  as 0004/0005.
- Not yet: supplier performance scores/price comparison, editing a PO after
  submission (cancel and re-create), invoices matched line-by-line to receipts,
  customer module. 116 tests pass, including receiving and payment on a
  1-connection pool.

## T. Business OS — Customers (Phase 6)

- `/admin/business-os/customers`: list/search (name, phone, email) and register. Walk-ins need only name + phone; email optional. Phones are normalised to E.164 (+256…) and unique, so registering an existing number reuses that customer.
- `/admin/business-os/customers/[id]`: edit details, preferred channel, marketing consent; purchase history (sales linked by phone); notes, complaints and warranty records timeline.
- POS: entering a customer phone at checkout registers/links the customer inside the sale transaction; a bad phone fails before any write; blank stays anonymous.
- Permission `customers.manage` (OWNER, MANAGER, CASHIER). Registration, edits (incl. consent) and notes are audit-logged.
- Migration `0007_business_os_customers.sql`: `customers.email` becomes nullable (relaxing), new columns, `customer_notes`, `sales.customer_id`. Deploy with the same push-after-backup approach as earlier phases.
- Limitations: repairs will join the timeline once built; online-store customers only appear via search; no merge tool for duplicates; no delete (by design).
- Tests: 126 passing locally (unit + integration on scratch Postgres); browser-verified on a production build.
